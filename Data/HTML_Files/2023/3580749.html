The Web has become an essential part of many people's daily lives, enabling them to complete everyday and essential tasks online and access important information resources. The ability to navigate the Web via the keyboard interface is critical to people with various types of disabilities. However, modern websites often violate web accessibility guidelines for keyboard navigability. In this paper, we present a novel approach for automatically detecting web accessibility barriers that prevent or hinder keyboard users’ ability to navigate web pages. An extensive evaluation of our technique on real-world subjects showed that our technique was able to detect navigation-based keyboard accessibility barriers in web applications with high precision and recall.

1 INTRODUCTION

Companies create web applications to reach a broad audience and enable customers to access services and information. The ability to access these daily-life resources with ease is important for everyone, especially for the approximately 15% of the world's population with disabilities [ 20 ]. Studies show that as much as 51% of the disabled population rely on the Web as a societal lifeline [ 6 ]. Unfortunately, sites on the Web pose many accessibility challenges for users with disabilities. As of 2022, less than 4% of the top million homepages on the Web meet the most widely used accessibility standards [ 37 ]. When web applications are poorly designed, they create barriers that threaten the goal of universal accessibility.

Keyboard navigation is one of the most important aspects of web accessibility that is often overlooked among web developers. Web users with limited vision or motor movement that cannot utilize a point-and-click or touch-operated device rely on keyboard commands to navigate a web application's User Interface (UI) via Assistive Technologiess (ATs). However, many of these ATs present information in web pages under the assumption that the keyboard navigation follows a linearized structure that is perceivable, which is often not the case. In modern web applications, changes and updates generated by JavaScript are not always presented to keyboard-based users interacting with the Web through ATs. Keyboard navigability is one of the most common and prevalent accessibility issues [ 22 , 25 , 28 ]. Studies show that as many as 29% of popular websites violate ways to help users navigate or find content/functionality, and 9% lack structural indicators for helping users orient themselves to determine where they are in a web page [ 75 ]. In this paper, we call the manifestation of these issues Keyboard Navigation Failures (KNFs) , which are, broadly, failures that prevent the user from intuitively navigating the web app's UI during keyboard interaction.

Detecting keyboard navigability issues is a challenging task due to the complex nature of modern client-side web applications. For example, identifying Keyboard Navigation Failures (KNFs) requires observing specific behaviors when navigating the UI via keyboard interaction. Simply analyzing the HTML source code or the rendering of the web page and its properties via static-based analysis techniques is not enough to expose the KNFs. In this paper, we present a novel approach for automatically detecting KNFs by using dynamic web crawling techniques to understand the navigation and the visual semantics of a web page's UI. An overview of our approach is shown in Figure 1 . The approach consists of two main parts. The first part builds models that capture the possible behaviors of a keyboard-based user's run-time interactions with the web page (Section 4 ). The second part analyzes these models to identify the navigation and visual behaviors that would represent KNFs (Section 5 ).

We implemented our approach as a prototype, BAGEL, to evaluate how well our technique could detect KNFs in real-world web applications. Our evaluation shows that BAGEL was able to accurately detect KNFs with an average F1 score of 90%. The key contributions of this paper are:

  1. The first formalization and modeling of Keyboard Navigation Failures (KNFs) as defined by the W3C.
  2. A fully automated KNF detection technique that outperforms state-of-the-art on real-world web applications.
  3. A study on a set of 20 real-world web pages that shows our approach is accurate in detecting KNFs.

2 BACKGROUND AND MOTIVATION

Keyboard usage is one of the foundational requirements for web accessibility and it is reflected in W3C Web Accessibility Initiative (WAI)’s Web Content Accessibility Guidelines (WCAG) 2.1. When interacting with a web page using a point-and-click device, every web control element, (i.e., a hyperlink) is available to be accessed. However, when interacting with a web page using a keyboard-based device, such access is sequential and depends on the keyboard navigation sequence. For example, during keyboard navigation, the user executes the Tab command to advance the keyboard cursor to the next (or Shift + Tab to go back to the previous) control element. The actuation keys ( Space or Enter ) are then used to activate the element that is currently in focus. Similarly, the Esc key is used to exit an active user prompt or dialog. Due to this sequential navigation, both the order of the sequence and the appearance of the keyboard cursor are crucial for keyboard-based users.

Navigation order is a significant aspect of a UI, especially for different ATs (e.g., parallel visual scanning, linear exploration using a screen reader, and serial navigation using a switch interface). However, design and implementation mistakes by web developers can hinder keyboard-based users’ ability to effectively navigate the UI. In this paper, we address the two general types of KNFs: Unintuitive Navigation Sequence and Unapparent Keyboard Focus , which are defined under WCAG Success Criterias (SCs) 2.4.3, 2.4.7, 3.2.1, and 3.2.2 [ 46 , 47 , 48 , 49 ]. These failures are all of the general keyboard navigation issues defined by WCAG that ensure that keyboard operability is intuitive and predictable. We describe each KNF next in detail.

2.1 Unintuitive Navigation Sequence

2.1.1 Unintuitive Navigation Order. An unintuitive order arises when the keyboard navigation is not sequentially consistent or intuitive with the meaning of the content. This can occur when developers (1) explicitly assign elements’ tabindex attribute with values greater than 0, or (2) reorder contents using the CSS float 1 , CSS Grid 1 , or CSS Flexbox Layout 1 modules to format elements [ 4 , 11 ], making the navigation order inconsistent from their visual order with respect to the Document Object Model (DOM) 2 . This creates an unexpected tab order, making the page less intuitive, and can skip certain elements entirely to disorient and confuse screen reader users.

An example of this is in Figure 2 ’s Disney World log-in page, where the navigation order is depicted by the bulleted numbers. In this example, the Password text-field (➋) and the “Forgot password?” link (➑) are visually adjacent to each other because their semantics are both associated with functionalities related to a user's password. This type of visual organization is the intuitive way developers design web applications. However, these two controls are not adjacent to each other in keyboard navigation. As a result, when the keyboard navigation advances from ➊, ➋, ➌, the functional semantics of the elements becomes inconsistent. The same applies to the “ Remember Me ” checkbox (➎) with respect to the Email and Password text-fields. From a blind user's perspective, when the controls with similar semantics are not grouped together, they could falsely believe the web form is at its end. For example, when they may navigate to the submit button (➌) without the awareness that there is still a “ Remember Me ” checkbox (➎).

As outlined in WCAG [ 42 , 43 ], a meaningful sequence should follow a linear visual flow of the page (e.g., header to content to footer).

2.1.2 Unintuitive Change-of-Context. Another scenario is when the web page changes its context (or focus behavior) unexpectedly during keyboard navigation. This “Change-Of-Context” KNF occurs when a UI/web functionality is actuated upon receiving keyboard focus or keyboard input without user awareness. An example resides in Figure 3 Mozilla ’s footer language selection drop-down component ( ). When this language drop-down is in focus and the user presses ↑ or ↓ , the drop-down's scripting directly activates the “next” (or previous) language selection and navigates to a new page of the selected language without the user's awareness. This can be disorienting, especially for a keyboard user because they were not advised about, nor confirmed the action to leave the current web page. According to WCAG Techniques G107 [ 26 ], an ideal implementation of this language drop-down is to be able to navigate across all of the available languages via ↑ and ↓ and activate the selected one via Enter (like how a mouse user would hover over their desired selection and click as shown in the figure).

As outlined in SC 3.2.1 and 3.2.2, unexpected changes of context can make interactive content less predictable and disorienting for keyboard-based users with visual disabilities or cognitive limitations so that they are unable to use the content.

2.1.3 Challenges to Detect Unintuitive Navigation Sequence. A naive way to detect Unintuitive-Nav-Order KNFs is to simply examine elements whose tabindex 3 attributes are set to a positive integer that overrides the default tab order. However, three challenges make this naive approach insufficient for our problem domain. First, a positive tabindex may not necessarily lead to inconsistent navigation – it may even lead to false-positives on accessible components implemented with the “roving tabindex” JavaScript techniques that provide focus by dynamically altering the tabindex attribute between -1 and 0 within a group of controls [ 10 ]. Second, there may be more than one “correct” navigation sequence, which itself can be dynamically altered via scripting during run-time. Third, it is difficult to examine and understand the semantics of a UI component's (e.g., drop-down list) JavaScript code that is responsible for event handlers. This is because the scripts may be dynamically loaded and not always available at the start of a web application. Scripting behaviors may also change as keyboard interaction enters different parts of the UI. These challenges make it difficult to detect Unintuitive-Nav-Order KNFs using traditional static program analysis techniques that only scan the HTML source code of the web page because interactive behaviors are not revealed in the page's source codes.

2.1.4 Closest Related Work to Unintuitive Navigation Sequence. The closest work related to Unintuitive Navigation Sequence is industrial web accessibility auditing tools that can detect general WCAG violations [ 18 , 29 , 30 , 31 , 36 ]. These tools can identify patterns in the HTML source code for missing page title, missing form labels, out of order or skipped heading levels (e.g., level < h3 > heading structured before level < h2 >), the lack of “skip navigation” shortcut links that allows ease of navigation, and the use of < table > to structure the visual layout rather than using CSS structural layout to help orient users within the content. While these techniques are capable of detecting simple layout inconsistencies, they cannot accurately detect KNFs (as we show in Section 6 ) that are dynamic in nature, because they are not capable of interacting with the web pages to reveal the behaviors of Unintuitive-Nav-Order KNFs.

KAFE [ 63 ] proposed a dynamic-based technique to detect UI elements that are not accessible to keyboard users [ 44 , 45 ]. It does not measure the consistency of keyboard navigation sequences and does not have a sense of the contextual information about a web page's content. Hence, it is not able to detect Unintuitive-Nav-Order KNFs.

2.2 Unapparent Keyboard Focus

A focus indicator [ 3 ] allows keyboard users to know their current location on a web page. By default, a basic focus indicator is provided by web browsers and is shown as an outlined border around the focused element (a focus ring). Form fields also show a vertical bar (text cursor) inside the field during text input. An unapparent focus type KNF occurs when the keyboard focus mechanism is not present or observable at all times, preventing the user from visually locating the interactive element that is ready to be activated or manipulated. More subtle failures occur when the surrounding background is visually similar to the custom focus style on a link or other controls or if their colors have insufficient contrast to be clearly noticed. Figure 4 shows The Guardian ’s login page. When the keyboard focus is navigated to the “ Continue with Apple ” button (➎), the button is highlighted with a faint grayish color ( #F6F6F6 ) that is not clearly visually distinguishable from its non-focused counterpart (with a color contrast ratio of only 1.08: 1). Similarly, when the focus is on the “ Enter your email address ” text-field (➏), the color contrast between the yellow focus ring ( #FFE500 ) and the white background ( #FFFFFF ) is only 1.27: 1.

As outlined in SC 2.4.7 any keyboard operable user interface is required to have a focus indicator that is visible. A corollary is defined [ 15 ] that requires the visual presentation of non-text (such as the focus indicator) to have a minimum contrast ratio of 3: 1 against its adjacent color(s).

2.2.1 Challenges to Detect Unapparent Keyboard Focus. A naive way to detect Unapparent-Focus KNFs is to examine the CSS applied to a web page to identify styling that removes or renders the visual focus indicator non-visible. However, this is troubled by two challenges. First, the focus indicator can be achieved in many different ways other than the CSS outlines 4 and borders 4 properties. For example, developers can change the presentation of UI components with inverted colors, highlights, or use JavaScript to animate the focus indicator with transitions from one element to another. Scripting can also be used to remove focus indicators upon receiving focus. This makes no determinant way to identify the visibility of focus indicators by examining specific CSS properties. Second, the intricacies of dynamic layout rendering can behave in unintuitive ways and be affected by surrounding elements. For example, run-time z-index 5 or outline-width 6 behaviors can cause the focus indicator of an element to be cut off, exceed the bounds, or be overlapped by other elements. Visual rendering becomes more complicated to examine when elements are rendered over background-images or background with opacity that are visually similar for the focus indicator to be clearly noticed. The dynamic layouts can also change as the user interacts or navigates the web page. These challenges make it difficult to detect Unapparent-Focus KNFs using traditional static program analysis techniques that rely on simply analyzing the rendered DOM of the web page when the page loads.

2.2.2 Closest Related Work to Unapparent Keyboard Focus. Several approaches have attempted to address UI navigation to easily identify the cursor location [ 67 ] and to efficiently select targets on the screen. Object Pointing [ 70 ] modifies the presentation of the mouse cursor based on Fitts's law [ 80 ] by overriding the default cursor behavior to jump from one element directly to another. SALEM [ 53 ] focuses on improving touch screen navigation for people with motor impairments by automatically repairing the insufficient sizes of touch targets. Similarly, Touch Guard [ 100 ] enhances UI elements’ touch areas with screen magnification to enlarge and disambiguate the bounds between multiple targets. While these techniques may improve users’ ability to interact with applications via mouse or touch-based interactions, they do not model the keyboard focus and therefore are not able to detect Unapparent-Focus KNFs.

3 RELATED WORK

There is extensive literature on detecting web content accessibility or usability issues. Here, we present other related works that cover similar concepts of accessibility or UI navigation, but do not directly address KNFs.

3.1 Techniques to Audit Web Accessibility

General strategies that address web accessibility include the detection of inaccessible layout properties and violations of accessible semantic structures. VizAssert [ 88 , 89 ] uses formal verification methods to attempt detection and repair of inaccessible layout properties. It makes an abstraction on the visual properties of the web page and then, uses efficiently-solvable SMT queries to automatically assert violations of visual layout and color-contrast consistencies. AxeRay [ 55 ] is an automated approach that infers semantic groupings of elements across various regions of a web page to test if these elements violate their WAI-ARIA roles’ semantic structure. These techniques specifically focus on accessibility relating to layout properties.

Acceptance web testing techniques, such as Pyccuracy [ 95 ] and Cucumber [ 32 ] have the potential to detect KNFs, but are not fully automated and require developers’ manual intervention. For example, these techniques allow developers to manually write or use scenario-based test cases to check keyboard accessibility requirements but the developers must anticipate the problems that may occur for each web page.

3.2 Usability of General UI Navigation

Navigation is a widely explored concept in usability research that investigates effective ways for users to interact with UIs. Such research spans across mobile, wearable, embedded, desktop systems [ 94 ], as well as websites [ 91 ]. Other work on usability [ 56 ] has focused on improving web navigability for low-vision users via screen magnification [ 57 , 59 , 60 , 77 , 99 ]. To mitigate the drawbacks of disorientation caused by magnification, overview+detail interface designs [ 71 , 74 , 78 ] were inspired to provide an overview of web pages with respect to their surrounding context for users to better locate the contents of interest. While these approaches can improve web accessibility from a visual perspective, they do not focus on the operability of a web page's UI via the keyboard.

Related work has used adaptive systems to improve performance in web navigation [ 73 ] related to tree structures [ 62 ], menu selection [ 66 ], and effective button placements [ 64 ] to reduce visual clutter in form design [ 76 , 87 ]. Harms et al. [ 72 ] proposed a design space analysis to support usability engineering that focuses on web forms. Supple++ [ 69 ] automatically personalizes web interfaces by adapting UI elements to meet the accessibility requirements for individuals with visual and motor disabilities. However, such adaptation techniques focus mainly on navigation via point-and-click devices such as a mouse, which does not relate to UI navigation issues that cause KNFs.

The understanding of a web page's semantic structure is a classic and long-standing research problem in addressing web navigability [ 61 , 85 , 98 , 101 ]. Sanoja et al [ 93 ] proposed web segmentation techniques to identify segments in web pages based on visual presentation style and spatial locality that are organized into semantic hierarchies. Furnas [ 68 ] employed a graph-based approach to model the relationship between web views and their outgoing navigation links by minimizing feasible navigation paths. Perona et al [ 90 ] used supervised machine learning techniques to detect web navigation problems based on client-side interaction data. Liu [ 79 ] focused on web mining to obtain real navigation features to learn anomalous attributes’ values to identify potential indicators for detecting navigation problems. Although these approaches have the potential to identify navigation inconsistency or to spot incorrect accessibility metadata used when navigating the web page via ATs, they do not fundamentally address KNFs.

A study by Alshayban et al. [ 54 ] examined accessibility issues that impact the Traversal Order of UI elements during linear navigation (e.g., via screen readers). However, the work only applies to the Android UI. Latte [ 92 ] and ATARI [ 102 ] are techniques that execute assistive services to detect navigation inconsistencies. However, Latte requires developers to manually provide test cases that are strictly tailored for specific test subjects and ATARI assumes the availability of a specific UI that is manually provided by the developers. These techniques can improve usability by debugging the inaccessibility that prevents a UI element and its functionality from being available to screen-reader users via TalkBack navigation. Though, it only works on Android applications and cannot be applied to keyboard accessibility in general.

4 MODELING KEYBOARD FOCUS FLOW

The goal of our approach is to automatically detect KNFs in web applications and identify the underlying faulty behaviors responsible for the failures. To address the aforementioned challenges, a key capability required to detect KNFs is to understand how the keyboard focus behaves in real-time when a keyboard user interacts with a web page. Our approach uses a dynamic crawling technique to interact with a web page by programmatically simulating user keyboard actions through the browser's keyboard API (e.g., executing Tab or Shift + Tab ) and retrieving the active element that is receiving focus for every such interaction. The way the keyboard focus indicator visually transitions between interactive elements is then translated into a graph-based abstraction representing the model that we will analyze. The approach defines a model, called the Keyboard Focus Flow Graph (KFFG) that captures (1) the keyboard navigation allowed by the Page Under Test (PUT) from the keyboard-based users’ perspective (Section 4.1 ), and (2) the ways the PUT is semantically structured and how the keyboard focus visually appears in the UI (Section 4.2 ). These models are used later to detect the undesirable behaviors caused by KNFs.

4.1 Building the Keyboard Navigation Model

4.1.1 Defining the Keyboard Focus Flow Graph. The keyboard navigation and focus-related properties of a PUT are represented by the Keyboard Focus Flow Graph (KFFG). The Keyboard Focus Flow Graph (KFFG) is formally represented as a graph ⟨ V , V s , E , V f , v 0 ⟩, where V is the set of nodes that consist of all visible elements in the UI, V s ⊆ V represents the set of all visible elements that are also interactive, E is the set of directed edges that represents the corresponding navigation flow among the interactive elements in V based on their keyboard focus, V f represents the sets of Functionally Similar Elements ( FuncSets ) that are characteristically/visually similar in the PUT, and v 0 is the entry node of the Keyboard Focus Flow Graph (KFFG).

A node v ∈ V s in the KFFG represents a UI element that is interactable (able to receive focus) to the keyboard that provides functionality with which the user can navigate, enter text, etc. V s includes all the native control elements such as HTML links < a >, inputs and form controls < button >, < input >, < select >, and < textarea > [ 14 ] as well as non-native control elements that have been customized with interactive characteristics. (e.g., elements with a tabindex property set with a non-negative integer, or elements binded with keyboard interactive events). Each node v is defined as a tuple ⟨ R , I , I ′, x ⟩, where R is the Minimum Bounding Rectangle (MBR) 7 that encloses v in the PUT, I and I ′ are the visual representations of R the way they are rendered in the browser before and after v receives focus, and x is the XPath representing v . R is defined as a tuple ⟨ x 1 , y 1 , x 2 , y 2 ⟩ where the coordinates ( x 1 , y 1 ) and ( x 2 , y 2 ) represent the upper left corner and the lower right corner of v . I ′ represents how the keyboard focus indicator is visually presented to the user when the focus is on v . The node v 0 ∈ V s represents the entry node of the graph. This is the element in the page that is the starting point for keyboard-based navigation.

A directed-edge e ∈ E is defined as a tuple ⟨ v s , v t , ϕ ⟩ indicating that the browser's keyboard focus shifts from a source node v s to a target node v t by pressing keystroke ϕ while v s is in focus. We include all standard keystrokes for web UI interaction where ϕ can be from the set of navigation keystrokes { Tab , Shift + Tab }, selection keystrokes { ↑ , ↓ , ← , → }, actuation keystrokes { Enter , Space }, and dismiss keystroke Esc [ 16 ]. In addition to detecting focus shifts, we detect any attempt for the page to navigate away to a different URL by instrumenting the onbeforeunload 8 JavaScript event. For such occurrences, we construct a forward edge e from the originating node to a special node added to the KFFG called v ext . (e.g., $ \langle v_{link}, v_{ext.}, {\bf \rm E{\small NTER}} \rangle$ ).

4.1.2 Constructing the Keyboard Focus Flow Graph. The KFFG model first builds the node set V by rendering the PUT in the browser and then analyzing its DOM to identify each unique HTML element. Each node is uniquely identified by its XPath in the DOM. The entry node of the graph v 0 is then identified by being the first element to receive focus.

The edge set E is then built by dynamically exploring the client-side UI to identify the possible keyboard navigation. The high-level intuition of this process is to iterate over all the interactive elements in the PUT (i.e., V s ) and execute all the keyboard operations (i.e., Φ) on each element to identify the resulting keyboard navigation. A challenge for dynamic UI exploration is its completeness. For example, during the crawling process, the keyboard focus may be obstructed by navigation behaviors, such as inaccessible custom widgets that trap navigation. This can halt the edge creation process and cause parts of the UI to be unexplored. Our technique overcomes this challenge by starting navigation at each possible interactive node, which skips anomalous navigation behaviors (such as loops) that may obstruct the exploration and ensures there will be no unexplored UI components in the PUT.

4.2 Building the Models to Capture Keyboard Focus Flow

While the keyboard navigation model provides us with information on how a keyboard user navigates around the UI, it alone cannot be used to detect KNFs. Our approach further builds models that contain (1) information about a web page's content that is needed to detect when the existing focus navigation is out of order. and (2) visual representations of the elements and their analyses needed to detect when the keyboard focus is visually absent during keyboard navigation.

4.2.1 Identify Similar Page Contents via Semantic Clustering. In order to give the notion of how intuitive the navigation is for the keyboard users (which we will discuss more in Section 5.1.1 ), the approach employs segmentation on the web page's content information to analyze the navigation. This is done by grouping the elements in V into FuncSets ( F 1 ,... F n ∈ V f ) that contain visually related elements in the web page. The goal of this step is to provide an abstraction of the way the web page's content information is structured and presented. Our observation is that related items in the PUT often exhibit consistency in visual presentation style and spatial locality that is used to depict the way users interact and navigate the web page. For example, a set of header menu, footer navigation, social media icons, or form elements that are spatially grouped together tend to be semantically oriented within the content of navigation. Our approach computes the visual similarity and DOM information similarity based on a distance function that uses several metrics such as matching the elements’ width, height, alignment, locality, as well as the similarities of their XPaths, CSS properties, tag-name, and class and text attributes. The process then uses a density-based clustering technique (DBSCAN) [ 81 ] that puts each element into only one cluster (i.e., hard clustering). Each element v ∈ V belongs in exactly one of the n clusters ( F i ⊆ V ) and all clusters are disjoint subsets of V .

4.2.2 Visual Representations of the Keyboard Focus Indicators. To understand whether the keyboard cursor (focus indicator) is apparent to keyboard users, the approach captures a set of visual representations of every node v ∈ V as the way they appear in a browser. This is done by capturing a screenshot that is cropped to the nodes’ R region both before ( I ) and after ( I ′) v is set to focus. Note that I and I ′ are identical in dimension. The cropping process includes a custom adjustable pixel radius as padding to ensure thick focus rings are not cut off. This visual focus model allows our approach to retain the exact way the focus would appear to a keyboard user during navigation.

5 DETECTING KEYBOARD NAVIGATION FAILURES

To perform the detection of Keyboard Navigation Failures (KNFs), the approach analyzes the keyboard navigation model that is constructed in Section 4.1 as well as the models that characterize keyboard focus constructed in Section 4.2 .

5.1 Detecting Unintuitive Navigation Sequence

To detect Unintuitive Navigation Sequence type KNFs, whose behaviors are described in Section 2.1 , the goal is to identify certain keyboard navigation patterns that represent KNFs. Recall that this general type of KNF can be either: Unintuitive-Nav-Order or Change-Of-Context failures. We explain the detection of each in detail in the following subsections.

5.1.1 Unintuitive Navigation Order. Recall that this KNF occurs when the navigation focus order is inconsistent with the determined reading order or the visual presentation of the web page [ 13 ] (e.g., the focus appears to jump around randomly across different sections of the PUT). To detect this KNF, the approach analyzes the keyboard navigation that is represented by the edges in the KFFG with respect to the FuncSet s. The intuition is that the FuncSets partition the PUT's layout into segments, each representing a semantically similar relationship in functionality (e.g., address web forms, header navigation bar, social media component, footer links). Let the FuncSets F 1 , F 2 ,..., F n of V be the n partitions, such that F 1 ∪ F 2 ∪ ... ∪ F n = V and $F_1 \cap F_2 \cap... \cap F_n = \varnothing$ , meaning that an element in the PUT can only reside in one (and only one) FuncSet . Navigation that follows sequences and relationships within the PUT's linear logical content flow should enter and exit each FuncSet exactly once. We define a failure ( true detection) as the existence of (1) more than one incoming Tab edge or (2) more than one Shift + Tab edge that enters a FuncSet V j . When there exists more than one way to navigate to a given FuncSet from either navigation direction, it represents that the focus violates the sequential navigation order of that partition. Such behavior means that the way a keyboard user encounters the elements in the partition does not follow the visual linear flow of the content within the partition.

In Figure 6 ’s example UI, the “Email” input textbox is semantically clustered with its adjacent “Forgot email” link (corresponding to the cluster F 2 in the KFFG). The same applies to the “Password” input textbox and the “Forgot password” link that form their own cluster (the cluster F 3 in the KFFG). A Unintuitive-Nav-Order KNF is identified because two Tab edges and two Shift + Tab edges can navigate to these two clusters in the KFFG.

Please note that our approach defines the nodes for the KFFG as the set of visible elements. Screen reader links that are not initially visible (e.g., skip navigation links or parallel links that are hidden for the sole purpose of providing labels for other control elements) are not used in our semantic clustering, thus, they will not be classified as KNFs.

5.1.2 Unintuitive Change-of-Context. This KNF occurs when the keyboard navigation triggers an unexpected change to the context of the PUT that lacks a prompt for users to abort the action. To detect this, the approach first examines if the special node “ v ext ” in the KFFGs has any incoming edge leading to it whose action ϕ is a non-actuation key (i.e., ϕ = Tab , Shift + Tab , ↑ , ↓ , ← , → ). Such an edge indicates an attempt to unload (navigate away from) the PUT through keystrokes that are not intended for activation. Per standard web design practices, non-activation keys are generally not intended to execute an action to confirm a web dialog prompt.

In Figure 6 ’s example UI, the language selection drop-down control contains an Unintuitive Change-of-Context KNF. The corresponding KFFG shows that three controls in the UI (i.e., the language selection drop-down, the “Help center” and the “Privacy” links) will cause a keyboard user to navigate away from the current page (as represented by the blue edges). In this example, only the language selection drop-down is identified as a KNF because it has an outgoing edge whose action ϕ is a non-activation action.

5.2 Detecting Unapparent Keyboard Focus

To detect Unapparent Keyboard Focus type KNFs, whose behaviors are described in Section 2.2 , the goal is to identify those interactive elements in the PUT that lack sufficient visual change when they receive focus during keyboard navigation [ 47 ].

The approach follows the focus appearance metrics as stated in the working draft of WCAG 2.2 [ 50 ] to determine what is considered sufficient focus (1) for the users that have difficulty perceiving UI components’ focus ring, and (2) for the users that have difficulties perceiving the difference in contrast from the focus ring. For a given UI element v , the definition of sufficient visible focus can be represented using the following definition:

\begin{equation} v_{\mathit {visible}} := \lbrace v \ | \ v \in V \ \wedge \ \mathcal {C}(v) \wedge \big (\mathcal {M}_1(v) \vee \mathcal {M}_2(v) \big) \wedge \mathcal {A}(v) \wedge \mathcal {O}(v)\rbrace \end{equation}
(1)
Here, the predicate $\mathcal {C}(v)$ represents the condition that satisfies a contrasting area ; the predicates $\mathcal {M}_1(v)$ and $\mathcal {M}_2(v)$ represent the two conditions for a minimum area ; the predicate $\mathcal {A}(v)$ represents the condition that satisfies adjacent contrast ; and the predicate $\mathcal {O}(v)$ represents the condition that satisfies obscurity of the element.

5.2.1 Contrasting Area. In order for an element's focus indicator to be considered visible, there must exist an area in the focus indicator that has a sufficient contrast ratio between the colors in the focused and unfocused states.

At a high level, detecting a contrasting area could be done by comparing the visual representation (screenshot) of every v ∈ V before and after they receive focus. Related work [ 82 , 83 , 84 , 86 ] has shown that differences in pixels can be used to reliably detect visual inconsistencies of HTML elements. Our approach identifies the visual differences between I and I ′ using perceptual image differencing (PID), a computer vision based technique for image comparison [ 96 ]. This visual difference is represented as the set of perceivable difference pixels DP Δ between I and I ′. The PID uses a Δ parameter as a customizable tolerance level to indicate how closely I and I ′ must match. We employed the parameters used in related research [ 85 ] used to address visual differences in web applications that constitute as presentation failures. If the PID determines that there is a sufficient human perceivable difference, this means there exists a set of pixels that are visually different between when the element is in focus versus not in focus (i.e., $DP_{\Delta } \ne \varnothing$ ). When such differences exist, the approach then analyzes the region of perceptual difference (i.e., DP Δ ) in the focused state (i.e., DP ∈ I ) and unfocused state (i.e., DP ′ ∈ I ′) to determine if the colors of the pixels in DP and DP ′ have sufficient contrast. To do this, for every pixel in DP , we find its corresponding pixel in DP ′ and compare the color value of these two pixels using the color contrast formula defined by WCAG [ 38 ].

Let x = ( x r , x g , x b ) and y = ( y r , y g , y b ) be a pair of dominant colors represented in their RGB colorspace, where x ∈ DP and y ∈ DP ′. The contrast ratio (CR) between them is mathematically defined by the relative luminance of the lighter color over the relative luminance of the darker color, as shown in Equation 2a , where L ( x ) is the relative luminance defined in Equation 2b and Equation 2c .

If there exists a pair of corresponding pixels that results in a Contrast Ratio (CR) of at least 3:1, then the contrast area CA is represented by the set of those pixels that satisfy the CR, otherwise, $CA = \varnothing$ . The predicate $\mathcal {C}(v)$ yields true if CA is not an empty set ( $CA \ne \varnothing$ ), otherwise, false.

5.2.2 Minimum Area. If there exists a contrasting area (i.e., $CA \ne \varnothing$ ), then our approach uses the two conditions to check whether the region covered by the set of pixels CA satisfies the threshold of a minimum area . The first condition (i.e., predicate $\mathcal {M}_1(v)$ ) requires CA ’s area to be at least as large as the area covered by the outline of a 1 CSS pixel (i.e., normatively defined as the absolute length px ) thick perimeter of the element's MBR. The second condition (i.e., $\mathcal {M}_2(v)$ ) requires CA ’s area to be at least as large as the area covered by a 4 CSS pixel thick line along the shortest side of the element's MBR. In order to translate these minimum areas from web rendering metrics into actual screen pixels, we capture the equivalent (before and after) screenshots of a dummy element for each element-under-test. We create such dummy elements by overriding the original element-under-test's focus events and CSS properties to portray a visible representation of these outlines, for each of the two conditions. We then use the difference in pixels of these dummy elements before and after they receive focus to calculate a pixel-based threshold for the minimum area for the original element-under-test. If $\mathcal {C}(v)$ yields true, then the predicates $\mathcal {M}_1(v)$ and $\mathcal {M}_2(v)$ respectively represent the two true/false conditions for a minimum area .

5.2.3 Adjacent Contrast. In addition to having a contrasting area CA with sufficient contrast between the colors in the focused and unfocused states (i.e., DP ′ and DP ), the element's focus component is also required to have sufficient contrast with respect to its surrounding color(s). In other words, DP ′ must satisfy CR against those pixels adjacent to the focus indicator region (i.e., I ′ \ DP ′) in the focused state.

Finding such an adjacent contrasting area is complicated by several challenges. The first challenge is that there is no corresponding 1:1 mapping to compare colors with when the pixels in DP ′ and I ′ \ DP ′ do not overlap each other. The second challenge is that browsers render text or shapes using anti-aliasing to smooth the color transition of edges by introducing some intermediate colors around the edges. The third challenge is that there are various styles of focus indicators (i.e., dotted lines or changes to background colors) that may consist of multiple color-related properties. These variants make checking adjacent contrasts ambiguous and difficult to achieve. To mitigate the ambiguity, our approach utilizes a color quantization method used in CV called Median Cut Quantization (MCQ) [ 97 ] to extract the dominant color(s) to reduce color noise. The intuition is that the visual difference region can be perceived as a single or discrete set of colors based on human perception. Instead of simply taking the average of the colors in DP ′ and I ′ \ DP ′, which may lead to an incorrect representation of colors, our approach uses Modified-MCQ (MMCQ) [ 7 ] to identify the dominating colors for a given image region using dimensionality reduction that decreases the number of colors used to find the n = 2 dominant colors in both DP ′ and I ′ \ DP ′. If there exists a pair of corresponding dominant colors in the set of all ordered pairs ( x , y ) ∈ ( DP ′ × I ′ \ DP ′), that yields a minimum CR of 3:1, then this predicate $\mathcal {A}(v)$ yields true, otherwise, $\mathcal {A}(v)$ yields false.

5.2.4 Obscurity. The approach also checks for whether the element with focus is not fully obscured or hidden by another page content [ 40 ]. To do this, we came up with heuristics to analyze the rendering of the web page. The heuristic first checks that the element itself is not a descendent of another element that is hidden with properties type="hidden" , visibility:hidden , or display:none . Next, the heuristic checks that the element is not obscured by another element. This is done by ensuring that the element does not collide with any other element's MBR where the other element is rendered above, according to “painting orders” defined by the CSS Positioned Layout [ 1 ] (i.e., the browser's rendering engine). All of these heuristics can be identified by analyzing the attributes of the elements in the DOM of the PUT when it has been rendered in the browser. The predicate $\mathcal {O}(v)$ yields true if the element is partially obscured or hidden, otherwise, $\mathcal {O}(v)$ yields false. Note that our approach can be customized to handle full obscurity [ 41 ]. This is done by checking if the element's MBR (i.e., R ) is fully contained by another element. Let $R_{e_1}$ and $R_{e_2}$ be the MBRs of elements e 1 and e 2 , e 1 is obscured (contained) by e 2 if $R_{e_1}.x_1 \le R_{e_2}.x_1 \wedge R_{e_1}.y_1 \le R_{e_2}.y_1 \wedge R_{e_1}.x_2 \ge R_{e_2}.x_2 \wedge R_{e_1}.y_2 \ge R_{e_2}.y_2$ .

Figure 7 demonstrates the process of analyzing the keyboard focus for an input form UI element. On the left, the element's unfocused (i.e., I ) and focused (i.e., I ′) screenshots are compared and used to determine the visually perceivable difference $DP_\Delta$ via PID. $DP_\Delta$ is then used as a filter to determine the area of focus in I and I ′, which are respectively denoted as DP and DP ′. The corresponding pixels in DP and DP ′ are then compared for color contrast to determine whether a contrasting area exists or not. Sufficient adjacent contrast is determined in a similar way by comparing the dominant colors in DP ′ versus I ′ \ DP ′ using MMCQ.

6 EVALUATION

To assess the effectiveness of our approach, we conducted an empirical evaluation that focused on two research questions:

RQ1: What is the accuracy of our technique in detecting KNFs in comparison with state-of-the-art approaches?

RQ2: How fast is our technique in detecting KNFs?

The detailed data of our evaluation is made available to the community via the project website [ 51 ].

6.1 Implementation

We implemented our approach as a Java-based prototype tool, called key B oard n A vi G ation failur E L ocator (BAGEL). The approach used Selenium WebDriver version 3.141.5, an automated browser testing tool to load, render, and interact with the subject web pages to build the KFFG model. In particular, the FirefoxDriver API [ 27 ] is used to send keyboard actions to the page and to execute JavaScript-based code to capture the change to the browser's keyboard focus. All web pages were rendered with a fixed screen resolution of 1920 × 1080 pixels on Firefox version 92.0. The approach also used iFix's [ 81 ] DBScan clustering to help identify the different FuncSets in a web page. We used aShot, a screenshot-capturing utility to capture a complete representation of the browser's viewport. We ran BAGEL and all experiments on a single AMD Ryzen 7 2700X 64-bit machine with 64GB memory and Ubuntu Linux 18.04.4 LTS.

Note that the setting that we used in our experiment to analyze Unapparent-Focus uses the minimum contrast ratio of 3.1 as defined in SC 2.4.11 Focus Appearance [ 39 ] and the partial obscurity as defined in SC 2.4.12 Focus Not Obscured [ 40 ], which are the minimum required levels of compliance, meaning they are the most critical thresholds to ensure websites meet the most essential needs of accessibility. Our approach is fully customizable to handle higher contrast ratios (e.g., 4.5:1 or 7:1) or full obscurity [ 41 ] for higher levels (e.g., AA or AAA) of WCAG compliance.

6.2 Subject Web Pages / Accessibility Tools

We conducted our evaluation on a set of 20 real-world subject web pages gathered from two sources. The first source is the Moz 500 top websites list [ 35 ] and the second source is a list of randomly selected websites that offer information, products, and services. We chose these two sources because together, they include government, education, as well as company websites that are obligated for accessibility as mandated by the ADA's Title II and Title III regulations [ 21 , 58 ]. To come up with the list of websites for the second source, we first used Google search to look for popular online government, university, community forums, e-commerce, and service websites. We searched the keywords “list of [genre] websites” for the five genres and included those that were listed under the “featured snippets” [ 24 ] of each search result (e.g., Science.gov, Harvard.edu, Twitch, eBay, Domino's Pizza). From these results, we compiled an initial list of 25 websites. To ensure our population was also representative of less popular sites, we extended this initial list using similarsites.com to randomly select two alternative websites of the same genre for each of the listed websites. Together, the second source consists of 75 unique websites. For the selection protocol, we randomly selected web pages from these two sources and manually interacted with them (following the WCAG Techniques used to identify KNFs) to include those that contained at least one type of KNF. The process was repeated until we had 10 subjects from each source. Note that our final set of 20 subjects did not include web pages from government and education websites because we did not observe any KNFs in these types of web pages that we encountered.

A challenge for our evaluation was that since the subject web pages represented popular and well-maintained websites, they were under constant evolution. To provide consistency in our results, we captured a complete version of each subject web page at the time we added it to the subject pool. To do this, we used mitmproxy [ 12 ] to store all the page's resources coming through HTTP/HTTPS traffic, including the JavaScript that is responsible for the web pages to remain interactive. The captured HTML, CSS, JavaScript, and other binary resources are packaged as local files to be loaded and replayed back by the proxy. For the few subjects that were not able to properly cache due to extra runtime security validation, we used web scraping tools [ 9 ], to capture the rendered resources directly from the DOM. Such a method is necessary for the subjects to behave the same as intended so our experiments could be repeatable.

To compare the effectiveness of BAGEL against current accessibility approaches, we selected available state-of-the-art tools from the Web Accessibility Evaluation Tools List [ 5 ] provided by W3C. Since there are no known tools that specifically target KNFs, we included prominent industry tools WAVE [ 18 ], ARC Toolkit [ 31 ], Axe DevTools Pro [ 23 ], Tenon Check [ 36 ] as well as a tool from the research literature QualWeb [ 65 ]. This set of tools offers the most complete analyses in handling a wide spectrum of issues that leverage analyses on the rendered DOM after scripting and CSS styling are applied [ 19 ]. We included these tools to see the helpfulness and extent their output can relate to KNFs.

6.3 Procedures

To answer RQ1 we ran BAGEL and measured how accurately it detected KNFs in the subject web pages. The accuracy was measured in terms of precision and recall for each of the three types of KNFs (Unintuitive-Nav-Order, Unintuitive Change-Of-Context, and Unapparent-Focus). To find the KNFs in each subject web page, the authors manually interacted with the page's UI and their underlying functional components via the keyboard to create the ground-truth. The process followed the Success Criterion defined by WCAG for each KNF type, including the testing techniques that point out objectively, the exact behaviors of the failures that a keyboard-based user would experience.

We analyzed BAGEL's output to check if it identified the actual element responsible for each KNF with respect to the ground-truth. We calculated false-positives, true-negatives, and false-negatives in an analogous way. For Unintuitive-Nav-Order, we included as the faulty elements, all of the elements contained in those clusters ( FuncSet ) where the navigation enters from more than one entry point. For Unintuitive Change-Of-Context, we included those elements that caused the web page to navigate away when some non-activation keyboard actions were performed on them. For Unapparent-Focus, we included those elements that did not have sufficient visible focus indication when receiving focus. These ways that we identify faulty elements follow the same workload pattern [ 52 ] that a developer would use the output of BAGEL (an outputted list of faulty elements) to debug the problems on a web page.

To measure how well BAGEL performed against other accessibility scanners, we ran the five state-of-the-art tools and measured how accurately they detected KNFs in the subject web pages. Since each tool had its own way of reporting detection, to make a comparison across the different tools, we objectively interpreted their outputted results based on violations to specific WCAG Success Criteria (SC). For these five tools, we considered reports with any mention of keyboard accessibility issues related to WCAG SC 2.4.3, SC 2.4.7, SC 3.2.1, and SC 3.2.2 as a KNF detection for the corresponding subject web page. We do this because these Success Criterias are the exact guidelines in which the KNFs were defined. For all five tools, our mechanism for recognizing a detection at the per-element level was consistent with the tool's intended usage and resulted in the most favorable accuracy scores for the tool.

To answer RQ2 , we measured the time it took to run the BAGEL tools on each subject web page. The running time included the time to start the tool, load the browser, build the models, and compute the detection results. For WAVE , ARC Toolkit , and Axe DevTools Pro , which are browser extensions, we included the time from when the detection was executed until the results were displayed. For Tenon Check and QualWeb , which are web-based services, we included the time to submit a subject link for analysis until the result page was displayed.

6.4 Discussion of RQ1 Results

6.4.1 Detection accuracy of BAGEL and other tools. The results of our experiments are shown in Table 1 and Table 2 , which respectively represent the KNF detection accuracy for BAGEL compared to other tools and the detailed accuracy for individual subjects. Generally, BAGEL was able to detect KNFs with higher accuracy compared to the other tools. None of the other tools are capable of detecting all three types of KNFs.

Table 1 shows that BAGEL was able to accurately detect the faulty element(s) responsible for each of the three types of KNFs with high precision and recall (with an F1 score of 93%, 83%, and 95% for the three types of KNFs). Tenon Check cannot detect any of the KNFs at all. Although WAVE had a higher precision than BAGEL in detecting Change-Of-Context KNFs, it failed to detect many and therefore had a low recall. Overall, the other tools ( Axe DevTools Pro , QualWeb , WAVE , and ARC Toolkit ) have only an average F1 score (across the three types of KNFs) of 15%, 23%, 43%, and 15% respectively. This shows that BAGEL does a much better job in detecting elements that are responsible for KNFs in the subject web pages. Table 2 shows that BAGEL was able to detect all the Unintuitive-Nav-Order KNFs in the subjects, all the Change-Of-Context KNFs in five out of six subjects that had this type of KNFs, and correctly detect all Unapparent-Focus KNFs in 14 out of 20 subjects that had this type of KNF.

6.4.2 Insights on What the Other Tools Detect. WAVE , Axe DevTools Pro , and ARC Toolkit , detect elements with Unintuitive-Nav-Order KNFs by scanning the DOM of a web page for elements with a tabindex value larger than zero. These elements are then outputted as potential issues. While this may be a simple proxy to detect potential order issues, a positive tabindex value does not always cause problems for page navigation. Therefore, these tools have higher rates of false-positives.All of the elements responsible for Change-Of-Context KNFs correctly identified by WAVE were menu-items binded with JavaScript onchange event handler that triggered a new page when an element in a menu was selected. WAVE was able to identify these KNFs by scanning the web page's DOM and identifying any menu with such an attached event handler. However, WAVE was not able to identify other cases of Change-Of-Context where an element needs to be dynamically interacted with to trigger this faulty behavior. This under-approximation caused WAVE to miss many such KNFs. For QualWeb , it considers any web form without a submit button to be a potential issue that impacts WCAG SC 3.2.2 and thus, a true detection. However, using this metric, QualWeb was not able to correctly identify any element with Change-Of-Context KNF.

In terms of Unapparent-Focus, QualWeb relies on scanning the DOM and the CSS applied to a web page to identify elements that do not have visible focus indications. However, since this is not a conclusive way of detecting Unapparent-Focus KNFs (as discussed in Section 2.2 ), QualWeb displays these as a potential warning that needs to be manually examined and verified by the users. While this can be very helpful, it can lead developers to miss many instances of Unapparent-Focus and requires them to examine many false positives. In fact, QualWeb was not able to detect 101 Unapparent-Focus KNFs, while 330 of the elements that QualWeb detected were false-positives.

6.4.3 Discussion of BAGEL's Negative Results. We investigated the KNFs that our approach incorrectly detected and found several scenarios where this occurred.

For Unintuitive-Nav-Order, the false detection was generally due to the inaccurate clustering of our FuncSets . For example, in the subject papajohns as shown in Figure 8 , the footer links of the page are presented in four categories “Our Company”, “Our Pizza”, “Help”, and “Career”. The similarity of these category headers was higher because they are made of < button > elements, thus, they were separately grouped together (into the dotted cluster) from the rest of the links in the footer. As a result, the keyboard navigation crossed between these two groupings multiple times (i.e., in the forward direction ➊ → ➋; ➍ → ➎ → ➏, etc.), which caused a false-positive detection because we do not consider this navigation as a Unintuitive-Nav-Order KNF.

For Unapparent-Focus, the inaccurate detections were usually due to screenshots not being correctly captured between the non-focused and focused states. In some cases, the screenshots resulted as empty white images or included black portions in the focused state, resulting in the perceivable difference and the contrast being falsely identified to be sufficient (false-negatives). In the subject arxiv , some extraneous pixels from other elements were included as part of the screenshot in the focused state. This caused the dominant color in the outer/adjacent region to be falsely identified, resulting insufficient contrast (false-positives). Another reason that resulted in false-negative detection (in subject leagueoflegends and lenovo ) was because the elements that lacked visible focus were also not accessible to the keyboard. Specifically, these elements were implemented using customized < div > and < h2 > that could not receive keyboard focus. As a result, Selenium WebDriver was unable to set these into focus to capture their screenshots. We also found examples in woot where the dummy elements that we used to capture the minimum area baseline could not be correctly created because the CSS could not be overwritten. This resulted in the minimum area threshold being set to zero and caused a false-negative detection.

6.5 Discussion of RQ2 Results

The run-time of BAGEL was significantly slower than the other five approaches. It took BAGEL an average of over 7.5 minutes to complete the detection for each subject. We analyzed the run-time breakdown of each individual step in BAGEL in detail and found that approximately 98% of the total time was spent on modeling and building the KFFG and only 2% was spent on the detection. As shown in Figure 9 , the KFFG construction process itself spent 59% of the time building the visual representation (screenshots) for the elements, 14% of the time building the keyboard navigation edges, and <1% of time performing the clustering on the elements. The average time for detecting all three KNFs was around 9 seconds (2% of total time) from the already constructed KFFGs.

BAGEL took much more time because it dynamically interacts with the subjects in the same way a keyboard user would. It also takes screenshots to capture what a sighted user actually sees during their interaction. The higher time cost is offset by its higher precision and recall. As an unoptimized prototype, we think that ∼ 8 minutes is a reasonable time in the context of software engineering (e.g., as compared to unit and integration testing tasks) and the current run-time can be improved. Strategies to reduce the run-time include deploying and distributing Selenium's processing across multiple cloud computing instances. Since the majority of the run-time overhead lies in extracting the web elements and capturing the screenshots, we expect that future improvements to Selenium as well as alternative capturing techniques would also improve BAGEL's run-time.

6.6 Reflection on the Root Causes of KNFs

We analyzed the subject web pages and found several implementation choices that contributed to the occurrence of the detected KNFs. Here, we look at the common root causes that we discovered from our study. This outcome can be useful for the developers to prevent these implementation mistakes from happening in the future.

The Unintuitive-Nav-Order type KNFs were usually caused by the developers explicitly assigning tabindex values to input controls. In our subjects, we found many instances where customized tabindex attributes were used to override the default tab order in order to automatically set the initial focus into input text-boxes where the user enters info (e.g., user id on a login page). Such implementations happened frequently on log-in forms, which is a common practice to seamlessly allow users to begin entering login credentials upon page load without extra navigation.

In terms of Unintuitive Change-Of-Context type KNFs, we discovered that they usually occurred when users change selections in custom drop-down widgets. These custom widgets often have their own scripting to trigger the unexpected Change-Of-Context. We found that the default Google Translate Widget [ 33 ] is also prone to this KNF despite it being implemented with a native < select > component. The scripting of the widget causes the web page to change as soon as users change the preferred language from its drop-down menu to automatically translate the web page.

For Unapparent-Focus type KNFs, we found that they frequently occurred under two scenarios. The first scenario was that there was no focus indication at all. This occurred when developers explicitly set the outline CSS property to outline:0 , outline:none or adopt custom CSS libraries or CSS Reset [ 8 ] to disable the browser's default focus outline. Upon investigation, we found this is a common practice among developers to ensure cross-browser aesthetics consistency. To maintain aesthetics, developers also override and hide the default outline with JavaScript to prevent the focused element from being highlighted when it receives programmatic focus from a mouse. Such practice may cause side effects that suppress the focus ring when certain screen readers fire mouse events to the browser from keyboard interactions (e.g., user presses Enter and the AT programmatically fires a mousedown event [ 2 ]). The second scenario is for a focus indicator to exist but then fail to meet the threshold of a minimum contrasting area. In such cases, the elements often do not have an explicit focus style applied to them, therefore resulting in a faint, dotted, black line supplied as Firefox's default focus indicator. This focus ring often does not itself passes the 1 CSS pixel thick perimeter outline minimum area threshold. However, when the element's MBR is large enough, the default focus indicator does have enough pixels to pass the second threshold criterion of a 4 CSS pixel thick line along the MBR's shortest side. Therefore smaller elements with default focus indicators tend to not have sufficient pixels to pass the minimum contrasting area.

6.7 Threat to Validity

A potential threat to construct validity is that our definition of KNFs may not match the intended idea of actual accessibility issues in the real-world setting. However, the use of this definition is reasonable because it is based on success criteria defined by WCAG, which is designed by accessibility experts from around the world and is used as a basis to determine websites’ compliance with ADA law [ 34 ]. As further validation, we conducted an empirical study of KNFs to qualitatively show the impact and severity of our detected KNFs from the two complementary perspectives of developers and users.

6.7.1 Feedback From Developers’ Perspective. We reached out to the developers of our subject web pages (via the websites’ contact forms, email, or their web app repository on GitHub) to report the discovered issues for feedback. Overall, out of the 12 subjects that we were able to reach out to, five developers acknowledged receiving our report, and two of them personally expressed the importance of our findings. We also received positive feedback from developers stating that they were addressing the issues or that our report could help improve the accessibility of their websites. After discussing the details of the reported KNF and confirming the replication of the issues, the Product Lead for Engadget stated that they will get the KNFs into the queue to promptly fix them. According to arxiv ’s Content Management team, repairing these issues (KNFs) “is extremely important to our mission” . In addition, we found that three of the subjects were partially fixed since we first reported the issues. Together, this represented positive validations for nearly half of the subjects. We believe that the positive responses that we received, alongside our reliance on the WCAG success criteria, show that the issues we are targeting represent real-world problems.

6.7.2 Feedback From Users’ Perspective. We included a small user study to gather feedback from two keyboard users with disabilities. The first user (U1) is a blind user that navigates the web via a screen reader and the second user (U2) is a sighted user with a motor disability that uses the keyboard instead of a mouse. We randomly selected six subject web pages (denoted as S1 to S6) and gave U1 and U2 five minutes to interact with each of the web page's core functionalities. We then discussed whether they found any difficulties with the navigation and how they felt the usability can be improved on this web page to make it more accessible. The result shows that, in general, both U1 and U2 did not find the web pages easy to navigate.

For Unintuitive-Nav-Order KNFs, based on U1’s interaction with S1 via a screen reader, he believed there was an issue with the flow, making it “not easy to understand at first” . However, he does not consider the navigation a major issue because the page size of S1 is relatively small, thus it was “not that difficult to manage” . When it comes S2, U1 believed the scattered information is more severe because he had to navigate back and forth more times to fully understand the content when the page is larger and more complex. He mentioned, “there's no way to jump around, especially when there's a toolbar” .

For Change-Of-Context KNFs, U1 did not encounter the KNF on S3 because he was using the VoiceOver screen reader on an iPhone, which displayed an iOS-based dialog to override the behavior of the faulty drop-down implementation. However, after informing U1 about the KNF, he expressed that the particular issue occurred to him often when browsing the web on a computer – especially noticeable in banking sites. U1 expressed that “It's frustrating for me because when you go down and it starts loading. Usually, I don't understand what happened until like later. Uh, maybe I did something wrong or something. You think that you made a mistake” . From U2’s sighted user perspective, he indicated the same issue with S4, that the web page “ended up redirecting me to a page that I did not want” .

For Unapparent-Focus KNFs, U2 expressed that during his interaction with S5, “It was difficult to see the highlighted areas. especially when I got to the end of the page, it was difficult to follow where the focus jumped back in the page.” He further emphasized that “It slowed me down. I also needed to spend time trying to find the highlighted item” . In terms of S6, where the keyboard focus indicator is completely absent visually, U2 mentioned “I did not know what was being selected on the web page. I was trying to select one of the options but not knowing where my cursor was, it was harder to know if I was selecting the correct option” .

In terms of improvements, U1 and U2 generally expressed the need to circumvent the failure of each KNF, including “making the page flow more direct and to the point” for Unintuitive-Nav-Order; “having a preview menu as well as being able to highlight the option without selecting it” for Change-Of-Context; and “having a noticeable, bolder highlighted areas around the selected part of the page” for Unapparent-Focus. These responses verified that what BAGEL identifies as KNFs aligns with issues faced by real-life users with disabilities that rely on keyboard navigation.

7 LIMITATIONS AND FUTURE WORK

7.1 Approach Limitations

A primary limitation of our approach is that it is only able to explore and identify KNFs in a single web page. In addition, within the single web page, the approach is only able to identify those KNFs that exist in the web page's initial UI state. For example, in modern Single-page applications, users can interact with a web page to trigger the appearance of different web components (e.g., hidden < div > panel or modal dialogs). If a faulty element is initially hidden when the page loads, only to become visible deeper down the navigation, our approach will not be able to analyze them. By integrating our KFFG modeling with a reliable crawling mechanism, we believe the approach can more completely explore web pages in the future.

7.2 Evaluation Study Limitations

A limitation of our evaluation is that our subjects are only a single web page within each of the selected websites. However, our sample selection process followed the Website Accessibility Conformance Evaluation Methodology (WCAG-EM) [ 17 ] to include web pages that cover (1) essential functionality of the website, such as the Log-In and Sign-Up page, (2) common and relevant key web pages, such as the Contact Us and Support page, and (3) a variety of content using different web technologies, such as Bootstrap, AngularJS, and WordPress plugins. The subjects cover different Rich Internet Application (RIA) technologies comprising modern HTML5 and custom JavaScript widgets, such as sliders, drop-down menus, and navigation menu components. Future work could broaden our findings by studying a broader set of subject web pages to identify more design and implementation mistakes that developers can make to cause KNFs.

Another limitation of our evaluation is that our tool is implemented and evaluated using Selenium's FirefoxDriver and there could be potential discrepancies between how different browsers show their default focus ring. For example, the styling of the default outline can vary by browser, where Edge and Firefox use a dotted line while Chrome and Opera use a blue focus outline. Our experiments are based on Firefox to create a lower bond baseline because Firefox has the least visible default focus compared to other browsers. It is important to note that these browser-specific KNFs could be easily detected by systematically running BAGEL using different Selenium WebDrivers for different browsers. As future work, we plan to expand the research to these implementations to identify browser-specific Unapparent-Focus KNFs and how a web page's keyboard focus accessibility differs across different browsers.

8 CONCLUDING REMARKS

Keyboard navigation accessibility barriers can hinder keyboard-based users’ ability to effectively and predictably interact with a web page's UI. In this paper, we presented a novel automated approach to detect navigation-based accessibility barriers related to focus navigation that are defined in WCAG, which we refer to as Keyboard Navigation Failures (KNFs). The approach builds a mathematical graph-based model to (1) capture the web navigation behaviors and (2) the focus appearance from a keyboard user's perspective to effectively detect KNFs. The empirical evaluation showed that our approach was able to successfully detect KNFs in a set of real-world subjects. The results, overall, are very positive and indicate that our approach can help developers detect keyboard navigation issues in their web applications. This work can potentially help improve WCAG conformance and can serve as a baseline for future automated testing to benefit people with various types of disabilities that depend on keyboard input.
